# النشر على Netlify

## الطريق القصير

انقر **«نشر المتجر»** على سطح المكتب — أو من هنا:

```bash
npm run deploy
```

يتولّى `scripts/deploy-netlify.ts` كل ما في هذا الملف بالترتيب: ينقل القاعدة
إلى Supabase إن لم تكن منقولة، ويثبّت أداة Netlify، ويفتح تسجيل الدخول،
وينشئ الموقع، ويضبط المتغيّرات الأربعة، وينشر، ثم يتحقق من الصفحات ويكتب
الرابط في `site-url.txt` على سطح المكتب — فتفتح أيقونتا «متجر الزبائن»
و«لوحة الإدارة» الموقع المنشور بدل الخادم المحلي.

ما تبقّى من هذا الملف شرحٌ لما يفعله، ومرجعٌ عند تعطّل خطوة.

---

المتجر **ليس صفحات ثابتة**: الأسعار والمخزون والطلبات تُحسب على الخادم.
Netlify يشغّله عبر دوال بلا حالة — وهذا يفرض ثلاثة أشياء عولجت في الكود:

| ما ينكسر بلا معالجة | ما فُعل |
| --- | --- |
| SQLite ملف على قرص مؤقت — الطلبات لا تُحفظ | PostgreSQL خارجي؛ المحوّل يُختار من `DATABASE_URL` تلقائيًا |
| رفع الصور يكتب في قرص يختفي عند كل نشر | مزوّد `netlify-blobs` في `src/lib/storage.ts` |
| عدّادات تحديد المعدّل في الذاكرة تتصفّر مع كل نسخة | جدول `rate_limits` في قاعدة البيانات |

> **ما لم يكن مكسورًا:** حظر تخمين كلمة مرور المدير كان في قاعدة البيانات
> منذ البداية (`login_attempts`)، فلم يتأثر. أخطر الثلاثة كان سليمًا.

## ١· قاعدة البيانات — Supabase

أنشئ حسابًا على [supabase.com](https://supabase.com) ثم مشروعًا جديدًا،
واحفظ كلمة مرور القاعدة التي يطلبها منك — لا تظهر ثانيةً.

ثم: **Project Settings ← Database ← Connection string**.

سترى ثلاثة روابط. **الاختيار بينها ليس تفصيلًا شكليًا:**

| الرابط | المنفذ | يصلح هنا؟ |
| --- | --- | --- |
| Direct connection | 5432 | ✗ يستنفد الاتصالات مع الدوال بلا حالة |
| Transaction pooler | 6543 | ✗ **يكسر إنشاء الطلبات** — اقرأ تحت |
| **Session pooler** | 5432 | ✓ **هذا هو المطلوب** |

> ### ⚠️ لماذا Transaction pooler يكسر المتجر
>
> إنشاء الطلب معاملة **تفاعلية** (`src/lib/services/orders.ts:142`)،
> وبداخلها حارس البيع الزائد الذي يخصم المخزون بشرط `stock >= quantity`
> (سطر 180). و PgBouncer في وضع transaction لا يضمن بقاء العميل على نفس
> الاتصال داخل المعاملة، فتفشل المعاملة أو — وهو الأسوأ — تنكسر ذرّيتها
> فيُباع مخزون غير موجود.
>
> Session pooler يبقي الاتصال للجلسة كاملة، فالمعاملات التفاعلية تعمل
> كما هي على خادم عادي.

انسخ رابط **Session pooler** وأضف إليه `?connection_limit=1`:

```
postgresql://postgres.PROJECT_REF:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres?connection_limit=1
```

> `connection_limit=1` يجعل كل نسخة دالة تفتح اتصالًا واحدًا لا مجموعة.
> بدونه تفتح كل نسخة عدة اتصالات فتستنفد حصة المشروع بسرعة تحت أي ضغط.

## ٢· بدّل المزوّد في المخطّط

سطر واحد في `prisma/schema.prisma`:

```prisma
datasource db {
  provider = "postgresql"   // كان "sqlite"
  url      = env("DATABASE_URL")
}
```

> Prisma يقرأ `provider` وقت البناء فلا يقبل قيمة من البيئة. أما **محوّل**
> الاتصال فيُختار من `DATABASE_URL` تلقائيًا (`src/lib/db-adapter.ts`).

## ٣· انقل بياناتك

قاعدتك الحالية فيها إعداداتك و٢٠ مدينة و١٠ تصنيفات ومنتجاك وحسابك.
الترحيلات تنقل **المخطّط** لا البيانات، فلا تتخطّ هذه الخطوة وإلا وجدت
متجرًا فارغًا.

```bash
# ١) صدّر من SQLite — افعله قبل تبديل المزوّد
npm run db:export          # ← data-export.json

# ٢) ابنِ ترحيلًا نظيفًا لـ PostgreSQL
#    ترحيلات SQLite لا تعمل عليه (أنواع مختلفة)
rm -rf prisma/migrations
DATABASE_URL="postgresql://…" npx prisma migrate dev --name init

# ٣) استورد
DATABASE_URL="postgresql://…" npm run db:import
```

ثم ضع نفس الرابط في `.env` المحلي لديك — فتعمل على نفس قاعدة الإنتاج بلا
اختلاف بين بيئتك والموقع.

> `data-export.json` يحوي **تجزئة كلمة مرور حسابك**. مستثنى من git
> بالفعل — لا ترفعه ولا ترسله في محادثة.

## ٤· صورك الحالية

`public/uploads` مستثنى من git، فصورتا منتجيك لن تصلا Netlify. أضفهما مرة
واحدة صراحةً:

```bash
git add -f public/uploads
```

تُخدَمان بعدها كملفات ثابتة، وكل صورة **جديدة** ترفعها من اللوحة تذهب إلى
Netlify Blobs تلقائيًا.

> ⚠️ أثر جانبي مقبول: حذف صورة قديمة من اللوحة يزيلها من المتجر لكن يبقي
> ملفها في المستودع. الصور الجديدة تُحذف فعليًا.

## ٥· الموقع على Netlify

اربط المستودع من [app.netlify.com](https://app.netlify.com) ← Add new site
← Import an existing project. أمر البناء ومجلد النشر يقرأهما Netlify من
`netlify.toml` تلقائيًا.

ثم **Site configuration ← Environment variables**:

| المتغيّر | القيمة |
| --- | --- |
| `DATABASE_URL` | رابط Supabase — **Session pooler** |
| `AUTH_SECRET` | ناتج `openssl rand -base64 32` |
| `NEXT_PUBLIC_SITE_URL` | `https://اسم-موقعك.netlify.app` |

`STORAGE_DRIVER` و`NODE_VERSION` مضبوطان في `netlify.toml` فلا تكررهما.

> `NEXT_PUBLIC_SITE_URL` يدخل في خريطة الموقع والبيانات المنظّمة وصور
> المشاركة على واتساب. تركه خاطئًا يعني روابط بلا صورة ولا عنوان، وفهرسة
> جوجل لعناوين لا وجود لها. عدّله ثانيةً عند ربط نطاقك الحقيقي، وأعد النشر.

## ٦· حساب المدير

حسابك انتقل مع البيانات في الخطوة ٣ بنفس كلمة المرور. لإنشاء حساب آخر:

```bash
DATABASE_URL="postgresql://…" npm run seed:admin
```

## ٧· بعد النشر — تحقّق

```bash
curl -I https://اسم-موقعك.netlify.app                      # 200
curl -s https://اسم-موقعك.netlify.app/sitemap.xml | head   # نطاقك لا localhost
curl -I https://اسم-موقعك.netlify.app/admin                # 307 إلى الدخول
```

وفي المتصفح — هذه الأربعة تحديدًا تُثبت أن المعالجات الثلاث تعمل:

1. سجّل الدخول للوحة ← قاعدة البيانات تعمل
2. **ارفع صورة منتج، ثم أعد النشر، ثم تأكد أنها ما زالت ظاهرة** ← Blobs يعمل
3. أنشئ طلب تجربة واحذفه ← الكتابة تعمل
4. اطلب `/api/orders/track` أكثر من عشر مرات ← يجب أن يرد `429`

## حدود تستحق معرفتها

**البدء البارد.** الدالة تنام بعد خمول، فأول زيارة بعد فترة أبطأ بثانية أو
اثنتين. ثم تعود سريعة.

**حصة Supabase المجانية** تكفي متجرًا صغيرًا، وقد توقف المشروع عند الخمول
الطويل فتتأخر أول زيارة.

**النسخ الاحتياطي.** Supabase يحتفظ بنسخ حسب خطتك. صدّر نسخة يدويًا بين حين
وآخر:

```bash
DATABASE_URL="postgresql://…" npm run db:export
```

**متى تنتقل إلى VPS؟** عندما تزعجك البدايات الباردة، أو تريد نسخًا
احتياطية تملكها، أو تكبر الطلبات. ملفات ذلك جاهزة في `deploy/README.md`
ولا تحتاج تعديل كود.
